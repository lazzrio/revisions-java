Semaine 1

Les bases de la POO

Une classe, ses attributs, ses méthodes. Comment lire au clavier, manipuler des tableaux, distinguer static et instance.

📚 Notions clés

Classe & objet

Une classe est un plan. Un objet est une réalisation concrète en mémoire, créée avec new.

class Train { }
Train t = new Train();

Attribut vs méthode

Un attribut = variable dans la classe (donnée). Une méthode = action que l'objet sait faire.

private int vitesse; // attribut
public void stopper() { } // méthode

Encapsulation

On rend les attributs private pour les protéger, et on expose des méthodes public pour y accéder.

private String nom;
public String getNom() { return nom; }

static vs instance

static = une seule copie partagée par toute la classe. Sans static = une copie par objet.

public static int i = 10; // partagé
public int j = 20; // par objet

Tableaux

Il faut allouer avec new avant utilisation. Taille via a.length (sans parenthèses).

int[] a = new int[5];
System.out.println(a.length);

Saisie clavier

Objet Scanner pour lire. Une méthode par type : nextInt(), nextDouble(), nextLine().

Scanner s = new Scanner(System.in);
int n = s.nextInt();

// Etudiant2026 — synthèse de la semaine
import java.util.Scanner;

class Etudiant {
    // ATTRIBUTS privés (encapsulation)
    private String nom;
    private int age;
    private double[] notes;
    private int nbnotes;

    Scanner clavier = new Scanner(System.in);

    // MÉTHODE de saisie avec validation while
    public int getAge() {
        System.out.println("Entrer l'age");
        age = clavier.nextInt();
        while (age < 18 || age > 25) {
            System.out.println("invalide, réessayer");
            age = clavier.nextInt();
        }
        return age;
    }

    // MÉTHODE qui saisit un tableau
    public double[] getNotes(int nb) {
        notes = new double[nb];  // allocation obligatoire !
        for (int i = 0; i < nb; i++) {
            do {
                System.out.println("Note " + (i+1));
                notes[i] = clavier.nextDouble();
            } while (notes[i] < 0 || notes[i] > 20);
        }
        return notes;
    }
}

static — l'exemple à comprendre

public class StaticTest {
    public static int i = 10;  // UNE SEULE copie partagée
    public int j = 20;         // UNE copie par objet
    final String NOM = "Segado"; // constante

    public static void main(String[] args) {
        StaticTest s1 = new StaticTest();
        StaticTest s2 = new StaticTest();

        s2.i++;                        // modifie la copie partagée
        System.out.println(s1.i);      // affiche 11 (partagé !)
        System.out.println(s2.i);      // affiche 11

        s1.j++;                        // modifie SEULEMENT s1
        System.out.println(s1.j);      // affiche 21
        System.out.println(s2.j);      // affiche 20 (indépendant)
    }
}

Exercice pratique — pas de code à lire, à faire toi-même

javac Train.java compile le fichier source en Train.class dans le même dossier src, s'il n'y a aucune erreur. Ensuite java Train exécute le programme (sans l'extension .class, juste le nom de la classe).

Si tu introduis une erreur volontaire (ex : oublier un ;, une accolade), javac refuse de produire le .class et affiche le numéro de ligne + la nature de l'erreur dans le terminal. C'est le comportement normal : la compilation échoue avant même de pouvoir exécuter quoi que ce soit.

cours1_train.zip — Train.java 
public class Train {
    public int vitesse, marche;
    public Train() { vitesse=0; marche=0; } // constructeur SANS paramètre
    public void stopper() { }  // méthode vide, à compléter
    public static void main(String[] argv) {
        Train trainsdi = new Train();
        trainsdi.stopper();
        System.out.println("Vitesse = "+trainsdi.vitesse);
    }
}

Constructeur par défaut = sans paramètre, appelé automatiquement par new Train(). Il initialise vitesse et marche à 0 pour garantir un état de départ cohérent, plutôt que de laisser des valeurs indéterminées.

Rôle de chaque bloc : le constructeur initialise, stopper() est destinée à remettre vitesse/marche à 0 (vide ici, à compléter), et main orchestre tout : crée l'objet, appelle stopper(), affiche l'état.

Conclusion : même si stopper() ne fait encore rien, l'affichage montre vitesse=0 car c'est le constructeur qui l'a déjà initialisé à 0 — la preuve que le constructeur s'exécute systématiquement avant tout appel de méthode sur l'objet.

cours1_string.zip — Main.java

Initialiser un String : String s = "texte"; (littéral, le plus courant) ou new String("texte") (équivalent en contenu). Chaîne vide : String vide = ""; (guillemets collés, sans espace) ou new String().

Concaténer : l'opérateur + — "abc" + "def" → "abcdef".

Copier : String s2 = s1; copie la référence (les deux noms pointent le même objet). Comme les String sont immuables, ça ne pose aucun problème pratique — contrairement aux tableaux vus plus loin.

String → int : int i = Integer.parseInt(chaine); — intérêt : pouvoir faire des calculs sur une valeur saisie au clavier (qui arrive toujours en String).

int → String : String s = String.valueOf(n); — intérêt : afficher/concaténer un nombre avec du texte proprement.

String → float : float f = Float.parseFloat(chaine); — même logique que pour int, pour les valeurs décimales.

cours1_arguments.zip — Main.java 
args = new String[]{"1", "2"};
System.out.println("Nom : "+args[0]);                      // ligne 4
System.out.println("Nom : "+Integer.parseInt(args[1]));    // ligne 5

Ligne 4 : args[0] vaut "1" (une String). L'affichage "Nom : 1" vient d'une simple concaténation de texte.

Ligne 5 : args[1] vaut "2" (String aussi), mais Integer.parseInt(args[1]) la convertit en int avant l'affichage. Le résultat affiché ("Nom : 2") ressemble à celui de la ligne 4, mais la nature de la valeur manipulée est différente : String pour la ligne 4, int pour la ligne 5.

À retenir : les arguments de main sont toujours reçus comme des String, même s'ils "ressemblent" à des nombres — il faut explicitement les convertir avec parseInt/parseFloat pour faire des calculs dessus.

cours1_statictest.zip — StaticTest.java 
public static int i = 10;
public int j = 20;
final String NOM = "Segado";
// ...

Ligne 11 — StaticTest.j : j n'est pas static, c'est un membre d'instance. On ne peut y accéder que via un objet (s1.j), jamais via le nom de la classe. Correction : écrire s1.j pour accéder via un objet, ou rendre j static si on veut vraiment y accéder via la classe.

Ligne 22 — s1.NOM="Java" : NOM est déclaré final, donc sa valeur est fixée définitivement à l'initialisation. Toute réaffectation est refusée par le compilateur. Correction : retirer final si on veut vraiment pouvoir réaffecter — mais ça casse l'intention (NOM n'est plus une constante).

cours1_train2.zip — Conducteur.java 
public class Conducteur {
    public static Train trainsdi = new Train();
    public static void main(String[] argv) {
        trainsdi.stopper();
        System.out.println("Vitesse = "+trainsdi.vitesse);
    }
}

Pourquoi static : sur trainsdi et sur main, ça permet d'utiliser l'attribut et la méthode sans créer d'objet Conducteur au préalable — cohérent avec le fait que main est toujours static (point d'entrée exécuté directement par la JVM).

Relation Conducteur/Train : Conducteur possède une référence vers un objet Train (attribut) — c'est une relation d'agrégation (Train existe "attaché" à Conducteur).

Instanciation et appel : public static Train trainsdi = new Train(); crée l'objet directement à la déclaration. trainsdi.stopper(); envoie ensuite un message (appel de méthode) à cet objet — "le conducteur n'a pas besoin de savoir comment le train s'arrête, c'est la responsabilité du train".

cours1_saisieclavier.zip — SaisieClavier.java 
Scanner clavier = new Scanner(System.in);   // déclaration + instanciation

Saisir un int : clavier.nextInt();

Fermer : clavier.close(); — libère la ressource système associée au flux clavier.

cours1_tableaux.zip — Main.java

Remarque sur la taille : elle n'est pas fixée à la déclaration (int[] a;) mais seulement à l'instanciation (a = new int[5];). Deux tableaux du même type déclaré peuvent avoir des tailles totalement différentes.

Manières d'instancier : new int[5] (taille explicite, cases initialisées à 0) ou en donnant directement les valeurs : int[] a = {1, 40, 3, 6, 3}; (taille déduite du nombre de valeurs).

Propriété de taille : a.length — c'est un attribut, donc sans parenthèses (contrairement à s.length() sur une String).

Parcourir : une boucle for classique, de i=0 jusqu'à i < a.length.

cours1_tableau_muldimension.zip — Main.java

Instanciation fixe : int[][] tab = {{11,12,13},{21,22,23}}; — dimensions et valeurs connues d'avance.

Instanciation "en escalier" : int[][] tab2 = new int[3][]; puis, ligne par ligne : tab2[i] = new int[taille]; — chaque ligne peut avoir une longueur différente (le tableau n'est pas obligatoirement rectangulaire).

Parcours : deux boucles for imbriquées — i pour les lignes (i<tab.length), j pour les colonnes (j<tab[i].length).

Nombre aléatoire : (int)(Math.random()*10) — Math.random() renvoie un double entre 0.0 (inclus) et 1.0 (exclu), qu'on multiplie par 10 puis qu'on caste en int pour obtenir un entier entre 0 et 9.

Suite de cours1_tableau_muldimension.zip 
int[][] tab3 = tab;  // copie la RÉFÉRENCE, pas le contenu
for (int i = 0; i < tab3.length; i++) {
    for (int j = 0; j < tab3[i].length; j++)
        System.out.print(tab3[i][j] + " ");
    System.out.println();
}

int[][] tab3 = tab; copie l'adresse du tableau, pas ses données. tab et tab3 désignent alors le même tableau physique en mémoire.

Conséquence directe : modifier une case via tab3 modifie la même case vue via tab — exactement le piège que tu as travaillé plus tôt dans cette conversation (question QCM sur tab3[0][0]=99).

TP1 — questions de réflexion officielles du sujet

Pourquoi séparer Main et Etudiant : ça respecte le principe d'encapsulation / séparation des responsabilités. Etudiant représente une entité métier (un étudiant et son comportement), Main représente le point d'entrée qui orchestre le programme. Mélanger les deux romprait la lisibilité et empêcherait de réutiliser Etudiant dans un autre programme.

Pourquoi on ne peut pas afficher directement eleve.nom depuis Main : les attributs de Etudiant sont déclarés private — accessibles uniquement à l'intérieur de la classe Etudiant elle-même. Depuis l'extérieur (Main), ils sont invisibles.

Solution proposée : exposer des méthodes publiques (ici afficherInfos(), et les getters comme getNom()) que Main peut appeler pour interagir avec l'objet, sans jamais toucher directement à ses attributs privés. C'est exactement le mécanisme d'encapsulation vu en semaine 1.

Relations entre classes (UML)

Comment les classes se parlent : héritage, agrégation, association, dépendance. Plus les mots-clés extends, super, protected.

🗺️ Les 4 relations UML

Héritage — "est-un"

Une classe fille récupère tout de la mère. Symbole UML : flèche à pointe triangulaire.

class Mammifere extends Vertebres

Agrégation — "a-un"

Un objet stocke un autre objet en attribut. Losange vide en UML.

class Config { public Ecran e; }

Association

Deux classes reliées, parfois via une classe intermédiaire qui a ses propres attributs.

class Mariage { Homme h; Femme f; }

Dépendance

Objet reçu uniquement en paramètre, jamais stocké. Flèche pointillée en UML.

public void manger(Os unOs) { }

protected — accès pour les sous-classes

public class Villain {
    protected int i;  // accessible dans Villain ET ses sous-classes

    public Villain(int i) { this.i = i; }
    public int read() { return i; }
    protected void set(int i) { this.i = i; }
}

public class Orc extends Villain {
    private int j;

    public Orc(int j) {
        super(j);       // appelle Villain(int)

        set(x);         // méthode protected héritée

    public void afficher() {

Les 5 mécanismes de l'héritage — un par un

Pas juste "comment les repérer" — ce que chacun fait vraiment quand le programme s'exécute.

Ça dit à Java : "un Mammifere EST UNE SORTE DE Vertebres." Concrètement, Mammifere reçoit automatiquement tout ce que Vertebres possède (méthodes publiques/protected), sans les réécrire.

Analogie : hériter d'une maison de famille — pas besoin de reconstruire les fondations, elles sont déjà là.

Un objet Mammifere contient deux parties : la partie "Vertebres" (héritée) et la partie "Mammifere" (propre). super(30) dit : "avant tout, va exécuter le constructeur Vertebres(int) avec 30."

public class Mammifere extends Vertebres {
    public Mammifere() {
        super(30);  // DOIT être la 1ère ligne
    }
}

Sans ça, la partie héritée ne serait jamais initialisée proprement — Java t'oblige à le préciser dès que le parent n'a pas de constructeur simple.

Différent de super(...) : ici on appelle une méthode normale du parent, pas le constructeur.

public void afficher() {
    super.afficher();   // exécute D'ABORD la version du parent
    System.out.println("...et un Orc !");  // PUIS ajoute ma ligne
}

Sans super.afficher(), la version du parent ne s'afficherait jamais — la méthode d'Orc remplace complètement celle du parent. super.methode() permet de réutiliser l'ancien comportement au lieu de le perdre.

⚠️ Aucun de tes fichiers réels de semaine 2 ne l'illustre — le cours en parle en théorie, mais aucun zip fourni ne le code concrètement. L'exemple ci-dessus est reconstruit pour que tu puisses le visualiser.

protected ne "fait" rien à l'exécution — c'est une règle de visibilité. Compare :

// AVEC protected
protected int i;
// dans Orc (sous-classe) :
System.out.println(i);   // ✅ ça marche

// AVEC private
private int i;
// dans Orc (sous-classe) :
System.out.println(i);   // ❌ ERREUR DE COMPILATION

protected = "je le cache au monde extérieur, mais je le montre à mes enfants (sous-classes)." Compromis entre private (personne) et public (tout le monde).

@Override ne change rien à l'exécution. Il sert uniquement à te protéger d'une faute de frappe.

@Override
public void Afficher() { ... }   // "A" majuscule par erreur !

Sans @Override : Java ne remarque rien, il crée juste une nouvelle méthode sans lien avec le parent — bug silencieux découvert bien plus tard.

Avec @Override : Java vérifie qu'une méthode afficher() existe vraiment dans le parent avec la même signature. Faute de frappe → erreur de compilation immédiate.

public class Article {
    public Entrepot unEntrepot;  // "est stocké dans" → référence retour
}
public class Entrepot {
    public Article[] stock;    // "contient" → tableau = plusieurs
    public void stocker(Article unArticle) { }
}

"Article est stocké dans Entrepot" : Article a un attribut Entrepot unEntrepot (référence vers son entrepôt).

"Entrepot contient au moins un Article" : Entrepot a un attribut Article[] stock — un tableau car il peut y en avoir plusieurs.

"Gardien de plusieurs articles" (cardinalité 0..* côté Article) : en Java, dès qu'une cardinalité dépasse 1, on utilise une collection (tableau, ou plus tard ArrayList<Article>) plutôt qu'un simple attribut objet unique.

Question conceptuelle sur diagramme UML

La relation typique Maison/Personne est une association (voire une agrégation) : une Personne "habite" une Maison. Une association relie deux classes sans hiérarchie particulière — contrairement à l'héritage, aucune classe n'est une "spécialisation" de l'autre.

Selon la cardinalité du diagramme (souvent 1 Maison ↔ 0..* Personnes), ça se traduit en Java par un attribut Personne[] habitants dans Maison, et/ou un attribut Maison maMaison dans Personne — selon le sens de navigabilité voulu (voir Exo 10 sur la navigabilité restreinte).

Multiplicités (cardinalités) UML 
class Oeuvre {
    private Livre[] livres;  // cardinalité 1..* côté Livre → collection
}
class Livre {
    private Oeuvre oeuvre;   // cardinalité 1..1 côté Oeuvre → attribut simple
}

Une Oeuvre "donne lieu à" plusieurs Livre (éditions, exemplaires) — cardinalité 1..* côté Livre. Inversement, un Livre est issu d'une seule Oeuvre — cardinalité 1..1 côté Oeuvre.

Règle générale du cours : une cardinalité supérieure à 1 se traduit toujours par une collection (tableau ou liste) ; une cardinalité 1..1 se traduit par un simple attribut objet.

cours2_classe_association.zip — Mariage.java 
public class Mariage {
    private String date, lieu;
    private Homme ungars;
    private Femme unefille;
    public Mariage(String pdate, String plieu, Homme h, Femme f) { ... }
}

Mariage possède deux attributs objets, l'un de type Homme et l'autre de type Femme — c'est la preuve concrète de l'association : la classe intermédiaire référence chacune des deux classes reliées.

Le constructeur impose de fournir les deux objets à la création (Homme h, Femme f) : un Mariage ne peut pas exister sans les deux personnes qu'il relie.

Classe-association participant à une autre relation 
class Mariage {
    private Contrat monContrat;  // peut valoir null → cardinalité 0..1
}

"Chaque mariage donne lieu ou pas à un contrat type" = cardinalité 0..1 côté Contrat. Ça se traduit simplement par un attribut objet optionnel dans Mariage : s'il n'y a pas de contrat, l'attribut vaut null.

Point important du cours : une classe-association (comme Mariage) peut elle-même participer à d'autres relations — ici, Mariage est à la fois l'association entre Homme/Femme, ET agrège un Contrat.

Association d'arité > 2 (revues / points de vente / semaines)

Une association à arité supérieure à 2 (plus de 2 classes reliées simultanément) ne peut pas être représentée par de simples attributs croisés entre deux classes.

Il faut une classe association à part entière qui référence toutes les classes concernées en même temps — même principe que Mariage (Exo 5), mais avec autant d'attributs objets que de classes reliées (ici 4 au lieu de 2).

cours2_agregation.zip — Configuration.java 
public class Configuration {
    public Ecran unEcran;
    public Clavier unClavier;
    public Disque unDisque;
}

Différence avec l'Exo 7 : ici pas de 5ᵉ classe intermédiaire — Configuration EST elle-même la classe qui agrège directement les 3 autres en attributs. Contrairement à l'association d'arité 4, aucune classe séparée n'est nécessaire pour porter la relation.

Preuve d'agrégation dans le code : les 3 attributs sont des objets d'autres classes, créés depuis l'extérieur (dans le main) puis simplement passés au constructeur — signe qu'ils existent indépendamment de Configuration (appartenance faible, pas de destruction en cascade).

cours2_pile.zip — Pile.java 
public class Pile {
    private Liste maListe;
    public Pile() { this.maListe = new Liste(); }  // créée DANS le constructeur
}

Relation Pile/Liste : composition (pas juste agrégation) — la Liste est créée directement à l'intérieur du constructeur de Pile, elle n'existe jamais indépendamment.

Différence agrégation/composition : en agrégation (Configuration/Ecran, Exo 8), les objets sont créés à l'extérieur puis simplement "reliés" — ils survivent indépendamment. En composition (Pile/Liste), l'objet composant est créé par le composé lui-même — son cycle de vie lui est entièrement subordonné.

Suppression du composé (Pile) : la Liste est supprimée automatiquement avec lui (appartenance forte).

Pour Configuration/Ecran (agrégation) : supprimer la Configuration ne supprime pas l'Ecran, le Clavier, le Disque — le cours le précise explicitement : "la destruction d'une configuration n'entraîne pas celle de ses trois composants, mais seulement la suppression du lien."

Navigabilité restreinte 
class Bibliotheque {
    private Livre[] livres;   // navigable → la Bibliothèque connaît ses Livres
}
class Livre {
    // PAS d'attribut Bibliotheque ici → non navigable dans l'autre sens
}

Navigabilité restreinte = la relation n'est utilisable que dans un seul sens. Ici, la Bibliothèque connaît ses Livres (attribut Livre[] livres), mais un Livre ne connaît pas sa Bibliothèque (pas d'attribut retour).

On peut donc naviguer de Bibliothèque vers Livre, mais pas l'inverse — exactement comme dans l'exemple du cours : "la bibliothèque connaît ses livres, mais il ne semble pas nécessaire à chaque livre de connaître la bibliothèque."

cours2_vertebres_heritage.zip 
public class Mammifere extends Vertebres {
    public Mammifere() { super(30); }
}

extends indique l'héritage de Mammifere par rapport à Vertebres.

⚠️ Piège dans l'énoncé : en Java, les constructeurs ne sont jamais hérités. C'est super(...) qui permet à Mammifere d'appeler (pas d'hériter) un constructeur de Vertebres.

Les 2 constructeurs de Vertebres : Vertebres() (sans paramètre, affiche "nombre inconnu") et Vertebres(int nbVertebres) (avec paramètre, affiche le nombre) — c'est de la surcharge de constructeur.

Implication dans le main : new Vertebres() appelle le 1er constructeur, new Vertebres(10) appelle le 2ᵉ, et new Mammifere() déclenche super(30) qui appelle le 2ᵉ constructeur de Vertebres avec la valeur 30 — donc affiche "nombre=30".

cours2_protected_villain_heritage.zip 
public class Villain {
    protected int i;
    public int read() { return i; }
}
public class Orc extends Villain {
    public Orc(int j) { super(j); this.j = j; }
    public void afficher() { System.out.println("valeur = "+i); }  // accès DIRECT à i
}

protected sur afficher() : permet à Orc d'accéder directement à i (attribut hérité de Villain) sans passer par un getter — c'est le sens même de protected : accessible aux sous-classes.

Dans le main de Main (hors hiérarchie Villain/Orc) : on ne peut pas écrire c.i directement, car i n'est pas public. Il faut passer par la méthode publique héritée : c.read().

super(j) dans le constructeur d'Orc appelle le constructeur Villain(int i) du parent avec j comme argument — ça initialise l'attribut i hérité de Villain.

cours2_transtypage.zip 
class Personne {
    private Personne conjoint = null;
    public void pacser(Personne p) { conjoint = p; }
}
public class Homme extends Personne { }
public class Femme extends Personne { }

Personne relie 2 objets via son attribut private Personne conjoint : un objet Personne peut référencer un autre objet Personne.

Dans le main de Test : marie.pacser(jean); — comme Homme et Femme héritent tous deux de Personne (extends), un objet Homme ou Femme EST une Personne (upcasting implicite). La méthode pacser(Personne p) accepte donc aussi bien un Homme qu'une Femme en argument, sans cast explicite nécessaire.

Attention

Pièges à anticiper

Piège 1super(...) doit être la 1ère ligne du constructeur.
Piège 2Si le parent n'a pas de constructeur sans paramètre, super(x) devient obligatoire.
Piège 3this(...) et super(...) incompatibles dans le même constructeur.
Piège 4Downcasting risqué : compile toujours, mais peut planter (ClassCastException).
Piège 5Agrégation ≠ Dépendance. Agrégation = stocké, dépendance = juste en paramètre.
Piège 6private du parent = non accessible directement dans la fille.
AstucePour reconnaître la relation en un coup d'œil : cherche extends (héritage), puis regarde les attributs (agrégation), puis les paramètres (dépendance).
